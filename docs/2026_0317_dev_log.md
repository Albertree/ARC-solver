# [2026_0317] ARCKG 개발 일지

ARC-solver → ARC-solver2 리팩토링 세션 전체 기록.  
아키텍처 재정립, 구조 수정, 구현 현황, 앞으로 할 일 포함.

---

## 1. 세션 개요

| 항목 | 내용 |
|------|------|
| 목적 | ARC-solver(원본)를 ARC-solver2로 클린 리팩토링 |
| 원칙 | 원본 코드는 스파게티 — 기능 재사용 최소화, 구조 독립 재설계 |
| Solver 방침 | SOAR가 유일한 solver. ARCSolver 등 별도 엔진 없음 |
| 언어/환경 | Python 3.9.6, 로컬 JSON 기반 semantic_memory |

---

## 2. 리팩토링 단계 요약

원래 계획한 7단계 중 이번 세션에서 완료한 범위:

```
1단계 — ARCKG 기반층          ✅ 완료
  memory_paths → pixel → object → grid → pair → task → comparison

2단계 — DSL층                 ✅ 완료 (기능 검증 생략, 후속 확인)
  util → selection → transformation → apply

3단계 — 로드/관리층           ✅ 완료
  managers/arc_manager → memory_system/working (→ agent/wm.py로 대체)

4단계 — 지식 분석 도구        ✅ 구조 정의 완료 (로직 구현 대기)
  (ARCSolver 역할 폐기 → SOAR operator 내부 도구로 흡수)

5단계 — 평가 환경             ✅ 완료
  env/arc_environment

6단계 — SOAR Agent            ✅ 뼈대 완료, 로직 구현 대기
  wm → elaboration_rules → rules → operators → active_operators
  → preferences → cycle → agent_common → active_agent

7단계 — 진입점               ✅ 완료
  main.py + run_task.py
```

## 3. 구조 수정 사항 (Correction)

### 3-1. 4단계 ARCSolver 폐기

| 기존 이해 | 수정 후 |
|-----------|---------|
| ARCSolver가 독립 solver, SOAR가 meta-reasoner | SOAR가 유일한 solver |
| SolverAgent가 ARCSolver 래핑 | SolverAgent 삭제 |
| program/ = 프로그램 합성 엔진 | program/ = anti_unification 도구만 남음 |

**삭제된 파일:**
- `workers/arc_solver.py`, `workers/__init__.py`
- `env/solver_agent.py`
- `program/manager.py`, `program/rules.py`
- `memory_system/working.py`, `memory_system/__init__.py`

### 3-2. WM 구조 재정립

Impasse를 "정보 필드"로 둔 것을 → "구조적 전이(structural transition)"으로 수정.

| 항목 | 기존 설계 | 수정 후 |
|------|-----------|---------|
| impasse | `wm.deficits` 필드 | `push_substate(trigger)` 메커니즘 |
| deficits | 사전 열거 | goal 하위 subgoal로 표현 |
| abstract_rule | WM 지식 영역 | LTM 저장, WM엔 포인터(active_rules)만 |
| operator 영역 | 없었음 | proposed_ops / selected_op / op_status 명시 |

### 3-3. Operator 일반화

도메인 특수 이름(`CompareGridPairOperator` 등)을 모두 제거.

| 기존 | 수정 후 |
|------|---------|
| `CompareGridPairOperator(pair_idx=0)` | `CompareOperator` (비교 대상을 WM에서 읽음) |
| `CompareObjectsInPairOperator(pair_idx=0)` | 동일 `CompareOperator` |
| `ExtractInvariantsOperator` | `ExtractPatternOperator` |
| `AntiUnifyOperator` | `GeneralizeOperator` |

비교 대상 선택은 별도 `SelectTargetOperator`가 담당.  
operator 이름에 TASK/PAIR/GRID/OBJECT/PIXEL 등 도메인 용어 사용 금지.

### 3-4. ElaborationRule 타이밍 수정

"사이클 시작 전 한 번 실행" → "매 사이클의 첫 번째 단계, Propose 이전"으로 명확화.

### 3-5. Impasse 조건 추가

기존: "operator failure만 impasse"  
수정: **"후보 없음(no_candidates)도 impasse"**

```
goal satisfied?        → 종료
op_status = failure?   → push_substate("failure")
후보 없음?             → push_substate("no_candidates")   ← 추가됨
```

## 4. 디테일 재정립

### 4-1. 노드 속성 vs. 비교 결과 분리

`id`는 비교 대상 속성이 아님. 저장 형식:

```json
{
  "id": "T08ed6ac7.P0.G0",
  "result": {
    "size": { "height": 3, "width": 3 },
    "color": { "0": false, "1": true, ... },
    "contents": [[...], ...]
  }
}
```

비교 결과 형식:

```json
{
  "id1": "...", "id2": "...",
  "lca_node_id": "...",
  "edge_id": "E_P0G0-P0G1",
  "order": 1,
  "result": { "type": "COMM|DIFF", "score": "2/3", "category": {...} }
}
```

### 4-2. GRID 속성 재정의

```python
{
  "size": { "height": int, "width": int },
  "color": { "0": bool, "1": bool, ..., "9": bool },
  "contents": [[int, ...], ...]
}
```

### 4-3. OBJECT 속성 재정의 (8개)

| 속성 | 설명 |
|------|------|
| `area` | bbox 내 0-9 색 셀 합계 (int) |
| `color` | `{"0": bool, ..., "9": bool}` |
| `coordinate` | bbox 내 색 있는 셀 좌표 집합 |
| `method` | Hodel objects() 함수 인자 3개 boolean dict |
| `position` | left_top / right_top / left_bottom / right_bottom (각 row_index, col_index) |
| `shape` | bbox 기반 2D array (색 있으면 1, 없으면 -1) |
| `size` | `{"height": int, "width": int}` (bbox 크기) |
| `symmetry` | 4종류 대칭 결과 boolean dict |

### 4-4. PIXEL 속성 재정의

```python
{
  "color": int,
  "coordinate": { "row_index": int, "col_index": int }
}
```

### 4-5. 환경이 에이전트에게 전달하는 것

기존(원본): `task_json` (dict)  
현재: `Task` 객체 (ARCKG 노드) — SOAR가 KG 노드 접근 필요

### 4-6. 시각화 색상 팔레트 (ANSI)

    3:  (46, 204, 64),    4:  (255, 220, 0),     5:  (170, 170, 170),
    6:  (240, 18, 190),   7:  (255, 133, 27),    8:  (127, 219, 255),

## 5. SOAR 아키텍처 상세

### 5-1. SOAR의 4개 구성요소

| 구성요소 | 역할 | 이 프로젝트의 파일 |
|----------|------|-------------------|
| Working Memory (WM) | 현재 문제 상태 전체. triplet(id, attr, value) | `agent/wm.py` |
| Production Memory | WM을 읽는 규칙 집합. Elaboration + Propose 규칙 | `agent/elaboration_rules.py`, `agent/rules.py` |
| Operators | WM을 바꾸는 행동 단위 | `agent/operators.py`, `agent/active_operators.py` |
| Cycle (결정 사이클) | Elaborate → Propose → Select → Apply 루프 | `agent/cycle.py` |

### 5-2. WM 구역 설계

```
S1 (루트 상태)
  ├── [목표 영역]
  │     goal.type = "predict_all_test_outputs"
  │     goal.subgoals = {test_0: {status: pending}, ...}
  │
  ├── [연산자 영역]
  │     proposed_ops = [op1, op2, ...]
  │     selected_op  = op
  │     op_status    = idle | running | success | failure
  │
  ├── [탐색 제어 영역]
  │     focus = {level, scope}
  │     comparison_agenda  = [{node_a, node_b, context}, ...]
  │     pending_comparisons = [...]
  │
  ├── [지식 영역]
  │     elaborated   = {}        ← 매 사이클 Elaborator가 채움 (파생 사실)
  │     relations    = {}        ← 비교 결과 누적
  │     invariants   = {}        ← COMM 속성 집합
  │     diff_patterns = {}       ← DIFF 속성 + 방향 패턴
  │     active_rules  = [...]    ← LTM rule에 대한 포인터 + confidence
  │
  └── [결과 영역]
        found = {test_0: grid, test_1: grid, ...}

S2 (impasse 시 동적 생성, 해결 시 소멸)
  ├── superstate = S1 참조
  ├── subgoal    = "find missing knowledge: ..."
  ├── proposed_ops / selected_op / op_status
  └── [S1과 동일한 구역 구조]

MAX_SUBSTATE_DEPTH = 2
```

### 5-3. 결정 사이클 흐름

```
┌─────────────────────────────────────┐
│  ① Elaborate (fixed-point)          │
│     ElaborationRule들 순회           │
│     condition(wm) → derive(wm)      │
│     → wm.elaborated 갱신             │
│     새 fact 없을 때까지 반복         │
├─────────────────────────────────────┤
│  ② Propose                          │
│     ProductionRule들 순회            │
│     condition(wm) → propose(wm)     │
│     → 후보 목록 수집                 │
├─────────────────────────────────────┤
│  ③ Select                           │
│     PREFERENCE_ORDER 기준 하나 선택  │
│     후보 없음 → impasse(no_candidates)│
├─────────────────────────────────────┤
│  ④ Apply                            │
│     operator.effect(wm)             │
│     → WM에 새 사실 추가              │
│     → op_status = success | failure │
│     failure → impasse(failure)      │
└─────────────────────────────────────┘
         ↕
  goal_satisfied? → 종료
  max_steps 초과? → 종료
```

### 5-4. Impasse 메커니즘

impasse는 "정보 필드"가 아니라 **구조적 전이**.

```
trigger: "no_candidates" (아무 operator도 제안 안 됨)
         "failure"       (operator가 실패함)

대응: wm.push_substate(subgoal, trigger)
  → S2 생성, S2 안에서 새 사이클 시작
  → S2 해결 → result를 S1에 전달 → wm.pop_substate()
  → depth >= MAX_SUBSTATE_DEPTH → 해결 불가, 종료
```

ARC에서 `no_candidates`가 발생하는 전형적 경우:  
지식 부족으로 다음 단계 precondition을 충족 못 할 때.

### 5-5. Operator 흐름

```
build_wm_from_task()
  → comparison_agenda에 example pair들의 (input, output) 쌍 등록

SelectTargetOperator
  → agenda에서 미처리 항목 꺼내 pending_comparisons로 이동

CompareOperator
  → pending에서 항목 꺼내 compare(node_a, node_b) 호출
  → wm.relations에 결과 추가

ExtractPatternOperator
  → wm.relations 순회
  → COMM → wm.invariants 추가
  → DIFF → wm.diff_patterns 추가

GeneralizeOperator
  → (invariants, diff_patterns) → 추상 규칙 생성
  → LTM(semantic_memory)에 저장
  → wm.active_rules에 {ref, confidence} 추가

PredictOperator
  → pending test subgoal 하나 선택
  → active_rules 중 최고 confidence 규칙으로 예측
  → wm.mark_subgoal_solved(test_idx, output)

SubmitOperator
  → all_outputs_found → op_status = "success" → goal 완료
```

### 5-6. Chunking (학습 메커니즘)

S2 subgoal이 해결될 때 트리거 (외부 reward와 무관).

```
substate 해결 시:
  chunk_from_substate(substate)
  → reasoning trace 압축 → production rule 생성
  → save_rule_to_ltm(rule, confidence)
  → semantic_memory/N_T{hex}/E_rule_N.json 저장
  → wm.active_rules에 포인터 추가
```

## 6. SOAR 강제 vs. 설계 자유

### SOAR가 강제하는 것 — 바꿀 수 없음

| 항목 | 내용 |
|------|------|
| WM 형식 | 모든 내용은 (identifier, attribute, value) triplet |
| 사이클 순서 | Elaborate → Propose → Select → Apply, 이 순서 불변 |
| Elaborate 타이밍 | 매 사이클 첫 번째 단계, 생략 불가 |
| Impasse 메커니즘 | 후보 없음 / failure → substate 생성, 예외 처리 금지 |
| Chunking 타이밍 | subgoal 해결 시 reasoning trace → production으로 압축 |
| S1/S2 계층 | 루트/서브스테이트 계층 구조 |
| op_status 기록 | operator 결과는 WM에 기록됨 (success/failure) |

### 설계 자유 — 전부 설계자가 결정

| 항목 | 결정 사항 |
|------|-----------|
| WM 내용 | goal 구역, 지식 구역, 탐색 제어 구역 설계 |
| Operators | 6개 (SelectTarget / Compare / ExtractPattern / Generalize / Predict / Submit) |
| Elaboration rules | 7개 파생 사실 규칙 |
| Production rules | 6개 (operator 1:1 대응) |
| Preferences | `select_target > compare > extract_pattern > generalize > predict > submit` |
| Subgoal 내용 | impasse 시 어떤 목표로 S2를 만들지 |
| MAX_SUBSTATE_DEPTH | 2 |
| max_steps | 50 |
| Chunking 결과물 | 압축된 production이 LTM에 저장되는 형태 |
| compare_fn 주입 | CompareOperator에 외부 함수 주입 가능 |
| generalize_fn 주입 | GeneralizeOperator에 외부 함수 주입 가능 |

## 8. 앞으로 해야 할 것 (구현 대기 목록)

### 최우선 — SOAR 로직 구현

아래 함수들이 현재 모두 `pass` 상태. 이것을 채우는 것이 핵심.

#### `agent/wm.py`
- `get(key)` — WM에서 값 읽기
- `set(key, value)` — WM에 값 쓰기
- `get_list(key)` — 리스트 값 읽기
- `update_dict(key, sub_key, value)` — dict 필드에 항목 추가
- `init_subgoals(test_count)` — test 개수만큼 subgoal 초기화
- `mark_subgoal_solved(test_idx, output)` — subgoal solved 전환
- `add_dynamic_subgoal(name, description)` — 동적 subgoal 추가
- `add_to_agenda(node_a, node_b, context)` — 비교 agenda에 추가
- `push_pending_comparison(...)` — agenda → pending 이동
- `pop_pending_comparison()` — pending에서 꺼내기
- `push_substate(subgoal, trigger)` — S2 생성
- `pop_substate(result)` — S2 소멸

#### `agent/agent_common.py`
- `build_wm_from_task(task, wm)` — Task 객체로 WM 초기화 (agenda 포함)
- `goal_satisfied(wm)` — found에 모든 test output 있는지 확인
- `answers_from_wm(wm)` — found에서 순서대로 추출

#### `agent/cycle.py`
- `run_cycle(wm, elaborator, proposer, max_steps)` — 전체 루프
- `_elaborate(wm, elaborator)` — fixed-point elaboration
- `_propose(wm, proposer)` — operator 후보 수집
- `_select(candidates, wm)` — 하나 선택
- `_apply(operator, wm)` — effect 호출
- `_handle_impasse(wm, trigger)` — substate 생성

#### `agent/elaboration_rules.py`
- 각 `ElaborationRule`의 `condition(wm)` 구현
- `Elaborator.run(wm)` — fixed-point 반복 엔진

#### `agent/rules.py`
- 각 `ProductionRule`의 `condition(wm)` 구현
- `Proposer.propose(wm)` — 후보 수집

#### `agent/active_operators.py`
- 6개 Operator의 `precondition(wm)`, `effect(wm)` 구현

#### `agent/active_agent.py`
- `ActiveSoarAgent.solve(task)` — 전체 흐름 연결

### 2순위 — 지식 분석 도구

Operator의 `effect()` 구현 시 필요한 내부 도구들:

- `ARCKG/comparison.py compare()` — 이미 구현됨, operator에서 호출
- `program/anti_unification.py anti_unify_pair_programs()` — 미구현 (GeneralizeOperator용)
- `procedural_memory/DSL/` — PredictOperator가 규칙 적용 시 사용

### 3순위 — 메모리 시스템

- `agent/memory.py chunk_from_substate()` — chunking 로직
- `agent/memory.py save_rule_to_ltm()` / `load_rules_from_ltm()` — LTM 연동

### 4순위 — 환경 연동

- `env/arc_environment.py`에서 `ARCManager._build_task_mapping()` 정적 메서드 필요
  (현재 인스턴스 메서드로만 구현됨 — 환경 초기화 시 에러 가능)
