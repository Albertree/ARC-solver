# Solver 흐름 통일 계획 (Inter vs Intra)

> **관련 문서**: 결핍 주도 탐색을 **SOAR 스타일 인지 아키텍처**로 구현하는 방안은 [soar_like_arc_solver.md](./soar_like_arc_solver.md)에 별도 정리되어 있다.

## 1. 현재 흐름이 다이어그램에 어떻게 매핑되는지

| 단계 | 다이어그램 노드 | 현재 코드 | 의미 |
|------|-----------------|-----------|------|
| T0   | Intra-TASK      | `_set_goal_from_task_and_pairs()` | TASK 하나를 받고, 풀 수 없으니 안쪽(PAIR)으로 진입 |
| P1   | Inter-PAIR      | `_compare_grids_across_pairs()` 중 example 간 비교 | PAIR들 간 property(그리드) 비교 |
| G2   | GRID (from P1)  | `_predict_test_g1()` (PaG1 예측) | PAIR들 **사이**의 GRID 관계로 test output 예측 |
| (G2 실패) | —           | 조건 분기 | PaG1 실패 시 다음 경로 선택 |
| P0   | Intra-PAIR      | `for pair_idx, pair in enumerate(example_pairs)` | **한 PAIR**을 선택해 자세히 봄 |
| G0/G1| Intra/Inter-GRID | `compare(pair.input_grid, pair.output_grid)` | 그 한 PAIR **안**에서 GRID 비교 (input↔output) |
| O2   | OBJECT (from G1) | OBJECT level 프로그램 생성·실행 | GRID 결과 ↔ output의 객체 비교 |
| X3   | PIXEL (from O2) | PIXEL level 프로그램 생성·실행 | OBJECT 결과 ↔ output의 픽셀 비교 |

**현재 실제 흐름:** `T0 → P1 → G2 → (실패 시) P0 → G0/G1 → O2 → X3`

---

## 2. 왜 “인위적”인가

- **한 구성요소 안으로 깊게 들어가는 것 (Intra)**  
  - T0 → P0 → G0 → O0 → X0  
  - “이 PAIR 하나를 연다 → 그 안의 GRID를 연다 → 그 안의 OBJECT → PIXEL”
- **상위 구성요소 간, 그 하위 구성요소들끼리 관계 보는 것 (Inter)**  
  - T0 → P1 → G2 → O3 → X4  
  - “PAIR들 사이를 비교한다 → 그때 쓰는 건 PAIR들 속 GRID들 → (필요 시 OBJECT/PIXEL까지 관계)”

이 둘은 **질문이 다르다**:
- Intra: “이 한 개체 **안**에서 무슨 변환이 일어나나?” → 프로그램 추출
- Inter: “여러 개체 **사이** 관계로 test output을 바로 정할 수 있나?” → PaG1 같은 직접 예측

현재는 **원칙 없이** “일단 P1→G2(Inter) 시도 → 실패하면 P0(Intra)로 점프”해서,  
“같은 레벨에서 Inter 먼저, 실패하면 Intra”가 명시적으로 설계된 게 아니라 **순서만 그렇게 되어 있어** 인위적으로 보이는 상태다.

---

## 3. 통일 원칙 제안: 두 가지 축을 명시

### 3.1 축 정리

- **축 1: 해결 전략**
  - **Inter 경로**: “여러 개체(PAIR/GRID/…) **사이** 관계만으로 정답을 정할 수 있는가?”  
    - 예: input 일치 → output 복사, example output 전부 동일 등
  - **Intra 경로**: “한 개체 **안**을 열어서 변환 규칙을 추출할 수 있는가?”  
    - 예: 한 PAIR의 input↔output 비교 → GRID/OBJECT/PIXEL 프로그램

- **축 2: 깊이 (레벨)**  
  TASK → PAIR → GRID → OBJECT → PIXEL.  
  “안으로 들어간다” = 다음 레벨로 가는 것.

### 3.2 통일 옵션 (계획 후보)

#### 옵션 A: “같은 레벨에서 항상 Inter 먼저, 실패 시 Intra”

- **원칙**: 각 레벨에서  
  1) 먼저 **그 레벨의 Inter**만으로 풀 수 있는지 시도하고,  
  2) 안 되면 **그 레벨의 Intra**로 “한 개체를 골라 그 안으로 들어간다”.
- **흐름**:
  - T0 (Intra-TASK: 문제 인식)  
    → **P1 (Inter-PAIR)** 시도 (PAIR들 간 비교·PaG1)  
    → 실패 시 **P0 (Intra-PAIR)** 선택 (한 PAIR 고름)  
    → **G0/G1 (한 PAIR 내 GRID)** 시도  
    → 실패 시 **G1에서 Inter-GRID**가 있으면 그쪽 시도 (필요 시)  
    → 그 다음 **O2, X3**는 “한 PAIR 안” 깊이 진행 (현재처럼)
- **장점**: “비교(Inter)로 안 되면 열어본다(Intra)”가 레벨마다 같은 규칙.
- **단점**: 지금처럼 “P1→G2 후 P0”이면, G2는 이미 “PAIR들 사이의 GRID”라서 레벨이 다름. “같은 레벨에서 Inter 먼저”를 엄격히 쓰려면 P1만 먼저 하고, P1만으로 예측 불가일 때 P0으로 가서, 그 다음에 “한 PAIR 안에서 G0”를 하는 식으로 단계를 나눠야 함.

#### 옵션 B: “두 파이프라인을 역할로 분리”

- **원칙**:  
  - **파이프라인 I (Inter)**: “관계만으로 예측” — T0 → P1 → G2 → (필요 시 O3, X4).  
    - 목적: PaG1 같은 **직접 예측**만. 프로그램 생성 없음.  
  - **파이프라인 II (Intra)**: “한 개체 깊이 분석” — T0 → P0 → G0 → O0 → X0.  
    - 목적: example **한 PAIR**에서 프로그램 추출 → test에 적용.
- **실행 순서**:  
  - (1) 파이프라인 I 실행 (가벼움). 성공하면 제출 후 종료.  
  - (2) 실패 시 파이프라인 II 실행 (무거움).  
- **장점**: “하나 안으로 깊게 들어가는 것”과 “상위 구성요소 간 하위 구성요소 관계 보는 것”이 **코드/설계상 완전히 분리**됨. 다이어그램의 Inter/Intra 두 갈래와 1:1 대응.
- **단점**: PaG1(G2)이 “P1의 하위 단계”로만 쓰이므로, “PAIR 레벨에서 Inter 먼저”라는 말을 “P1만 먼저”로 제한할지, “P1+그 다음 G2까지”를 한 덩어리로 볼지 정해야 함.

#### 옵션 C: “깊이 우선(Intra) 한 번 끝까지, 필요 시 Inter 보조”

- **원칙**:  
  - 기본은 **한 PAIR 안으로 끝까지 들어가기** (T0 → P0 → G0 → O0 → X0)로 프로그램을 만든다.  
  - **Inter(P1, G2)** 는 “예측만으로 풀 수 있는지 **먼저** 한 번 시도”하는 **사전 필터**로만 사용.  
    - 즉, “구조적으로 Inter가 먼저”가 아니라 “비용이 작은 시도를 먼저”로 정의.
- **흐름**:  
  - 1) (선택) PaG1 시도 (P1+G2). 성공 시 종료.  
  - 2) 실패 시 “본격 해결”은 항상 Intra: P0 → G0 → O0 → X0.  
- **장점**: 현재 구현과 가장 비슷하게 맞출 수 있음.  
- **단점**: “Inter vs Intra 통일”보다는 “저비용 시도 먼저”에 가까워서, 다이어그램의 계층/Inter–Intra 구분이 코드에서 드러나지는 않을 수 있음.

## 4. 권장 방향: 옵션 B + 다이어그램와 1:1 대응

- **Inter 파이프라인**  
  - T0 → **P1 (Inter-PAIR)** → **G2 (PAIR들 사이 GRID, PaG1)** → (필요 시 O3, X4).  
  - 여기서 하는 일만 “상위 구성요소 간 하위 구성요소 관계로 예측”. 프로그램 생성 없음.
- **Intra 파이프라인**  
  - T0 → **P0 (Intra-PAIR, 한 PAIR 선택)** → **G0/G1 (그 PAIR 안 GRID)** → **O2, X3**.  
  - 여기서만 “한 하위 구성요소로 깊게 들어가서” 비교·rule·프로그램 생성.

이렇게 하면:
- “하나의 하위 구성요소로 깊게 들어가는 것” = Intra 파이프라인 전체
- “상위 구성요소 간 하위 구성요소 관계” = Inter 파이프라인 전체  
로 통일되고, 다이어그램의 cascade와도 맞다.

## 5. 코드 쪽 변경 방향 (요지)

1. **진입점 분리**
   - `test()` 상단에서 **파이프라인 이름**을 명시:  
     `run_inter_pipeline()` vs `run_intra_pipeline()` (또는 같은 함수 안에서 `phase = "inter" | "intra"`).
2. **Inter 파이프라인**
   - 현재의 `_compare_grids_across_pairs()` + `_predict_test_g1()` 를 한 덩어리로 묶고,  
     “PAIR 간 비교만으로 예측 시도, 성공 시 즉시 return”으로 문서화.  
   - (나중에) O3, X4가 필요하면 “Inter-OBJECT / Inter-PIXEL” 확장 시 같은 파이프라인 안에 추가.
3. **Intra 파이프라인**
   - PaG1 실패 후에만 진입.  
     “example_pairs를 하나씩 선택(P0) → 그 pair 안에서 GRID(G0/G1) → OBJECT(O2) → PIXEL(X3)”만 수행.  
   - “PAIR들 간 GRID 비교”는 이 파이프라인에서는 호출하지 않음 (이미 Inter에서 함).
4. **로깅/주석**
   - 각 단계에 다이어그램 노드 라벨 부여:  
     예) `# [Intra] P0: PAIR {pair_idx} 선택`, `# [Inter] G2: PaG1 예측 시도`.

## 6. 요약

- 현재 흐름은 **T0 → P1 → G2 → P0 → G1 → O2 → X3** 로 보는 게 맞고,  
  **Inter(P1, G2)를 먼저 시도한 뒤, 실패 시 Intra(P0, G0/G1, O2, X3)로 점프**하는 구조라서 인위적으로 보임.
- 통일을 위해 **“한 구성요소 깊이(Intra)”와 “구성요소 간 관계(Inter)”를 두 개의 명시적 파이프라인으로 나누고**,  
  **실행 순서(Inter 먼저 vs Intra만)** 를 옵션 A/B/C 중 하나로 고정하는 것**을 제안함.
- 다이어그램과의 대응과 개념 정리를 중시하면 **옵션 B (두 파이프라인 역할 분리)** 로 정리하고,  
  위 5번처럼 진입점·파이프라인·로깅을 나누면 “흐름이 통일되었다”고 말하기 좋다.

## 7. 대안: 결핍 주도 탐색 (Deficit-Driven Search)

**목표**: 전체를 complete하게 탐색하는 고정된 방법이 아니라, **현재 부족한 것을 인지하고, 그 부족한 것을 채우기 위해만** 탐색을 유도한다.

### 7.1 원칙

- **질문**: “지금 무엇이 부족해서 문제를 풀지 못하는가?” → 그 **결핍(deficit)** 을 채우는 행동만 한다.
- **탐색 유형**은 두 가지로 한정:
  1. **범위 확장 (scope expansion)**: 같은 레벨에서 다른 개체(다른 grid, 다른 pair)를 보며 “부족한 속성/관계”를 찾는다.
  2. **깊이 진입 (go deeper)**: 현재 레벨에서는 그 결핍을 채울 방법이 없다고 판단되면, 하위 구성요소(OBJECT, PIXEL)를 본다.

즉, “항상 Inter 먼저”나 “항상 Intra 먼저”가 아니라, **“지금 필요한 게 뭔가?”에 따라** 다음에 할 일(범위 확장 vs 깊이 진입)이 결정된다.

### 7.2 예시 흐름 (말한 대로 정리)

1. **TASK 수신** → 현재 정보만으로 문제 해결 시도 → **불가** → TASK 내부를 들여다본다.
2. **TASK 내부**: PAIR들이 보임. **PAIR들의 property만** 비교 → 이만으로는 해결 **불가** → PAIR 내부를 들여다본다.
3. **한 PAIR 내부**: GRID가 보임. **GRID property**(예: size, color, contents)를 비교해 보니, “이 세 가지를 만들면 출력을 만들 수 있다”고 **판단**하지만, **만들 근거가 부족**함 (특히 **contents**).
4. **결핍**: “output grid의 **contents**를 정할 근거가 없다.”
   - **범위 확장**: 다른 grid, 다른 pair의 grid까지 살펴서 “contents를 정할 수 있는 정보”를 찾는다.
   - 예: test input과 동일한 contents의 output grid를 찾으면 → 그 output을 쓰면 됨 (**PaG1 예측 성공**).
   - **실패**: 그런 grid를 찾지 못함 → “grid contents를 이 레벨에서 예측할 방법이 없다”고 판단.
5. **깊이 진입**: GRID의 하위 요소인 **OBJECT**를 살펴본다.
6. **OBJECT 단계** (같은 원칙 적용):
   - 먼저 **한 grid 안**에서 object들 간 속성 비교 (같은 grid 내 object–object).
   - 부족하면 **서로 다른 grid**에 있는 object들 비교.
   - 더 부족하면 **서로 다른 pair**의 object들까지 비교.

정리하면: **한 레벨에서 “필요한 속성/관계”가 부족하면**  
- 우선 **같은 레벨에서 범위만 넓혀서** (다른 grid, 다른 pair) 그걸 채울 수 있는지 보고,  
- 채울 수 없으면 **한 단계 깊이** 들어가서 (OBJECT → PIXEL) 같은 식으로 “무엇이 부족한가”를 보고 탐색한다.

### 7.3 설계 요지

| 개념 | 설명 |
|------|------|
| **결핍(Deficit)** | “지금 출력(또는 중간 결과)을 만들기 위해 필요한데, 아직 값을 정하지 못한 것” (예: output grid의 **contents**). |
| **판단** | “이 레벨의 property만으로 출력을 만들 수 있다/없다”, “contents를 정할 근거가 있다/없다” 등을 명시적으로 판단. |
| **범위 확장** | 결핍을 채우기 위해 **같은 레벨**에서 다른 개체(다른 grid, 다른 pair)를 본다. PaG1은 “grid contents 결핍 → 다른 pair의 grid를 봐서 같은 input의 output 복사”에 해당. |
| **깊이 진입** | “이 레벨에서는 결핍을 채울 방법이 없다”고 판단될 때만, **하위 레벨**(OBJECT, PIXEL)로 들어간다. |

### 7.4 구현 방향 (개념)

- **상태**: 현재 “무엇을 만들려고 하는지”(목표 출력/중간 표현)와 “어떤 속성이 아직 비어 있는지”(결핍 목록)를 유지.
- **한 스텝**:
  1. 결핍이 없으면 → 출력 제출 또는 다음 목표로.
  2. 결핍이 있으면 →  
     - (A) **현재 보는 범위 안**에서 비교/추론으로 그 결핍을 채울 수 있는지 시도.  
     - (B) 채울 수 없으면 **범위 확장** (다른 grid, 다른 pair까지 같은 레벨 비교).  
     - (C) 범위를 넓혀도 채울 수 없으면 **깊이 진입** (하위 레벨로 이동 후, 그 레벨에서 다시 1–2 적용).
- **PaG1**: “output grid의 contents가 비어 있음(deficit)” → (B) 다른 pair의 grid를 보니 “test input과 같은 input을 가진 example이 있고, 그 output을 쓰면 됨” → contents 채움 → 성공. 실패 시 (C) GRID 하위인 OBJECT로 진입.

이렇게 하면 “원하는 정보만 탐색”할 수 있도록, **결핍이 이끄는 탐색**으로 흐름을 통일할 수 있다.

### 7.5 결핍 → 탐색 결정: 어떻게 정하는가

**질문**: “결핍이 무엇이기 때문에 어떤 것을 탐색한다”는 것을 **어떤 규칙으로** 결정하는가?

#### (1) 결핍을 “채우는 방법”은 두 가지뿐

어떤 결핍이든 값을 채우는 방법은 구조적으로 두 가지로 한정할 수 있다.

| 방법 | 의미 | 탐색 대상 |
|------|------|-----------|
| **같은 레벨에서 복사/매칭** | 이미 다른 개체에 그 값(또는 그 값을 정할 수 있는 관계)이 있다고 가정 | **같은 레벨의 다른 개체** (다른 grid, 다른 pair 등) |
| **하위 레벨에서 조합** | 그 값은 하위 구성요소들(OBJECT, PIXEL)의 결과로 “만들어져야” 한다고 가정 | **현재 레벨의 하위 구성요소** (GRID → OBJECT → PIXEL) |

그래서 **결핍이 무엇인지**가 정해지면, “어떤 것을 탐색할지”는 위 두 가지 후보 안에서만 고르면 된다.

#### (2) 결핍의 “위치”로 탐색 범위를 정한다

- **결핍의 위치**: “어느 레벨·어느 속성을 비우고 있는가?”  
  예: `output_grid.contents`, `output_grid.size`, `output_objects[].position` 등.
- **규칙**:
  - **같은 레벨에서 채우기** → 탐색 = **그 레벨의 다른 개체들**.  
    - 결핍이 “output **grid**의 contents”이면, 탐색은 “**다른 grid**들” (같은 pair의 input grid, 다른 pair의 input/output grid).  
    - 결핍이 “한 **object**의 속성”이면, 탐색은 “다른 **object**들” (같은 grid 안, 다른 grid, 다른 pair).
  - **하위에서 채우기** → 탐색 = **그 개체의 하위 레벨**.  
    - 결핍이 “grid의 contents”인데 같은 레벨에서 매칭 실패 → 탐색은 “그 grid의 **OBJECT**들”, 더 실패하면 “**PIXEL**”.

즉, **결핍이 무엇(어떤 속성·어느 레벨)인지**가 정해지는 순간, “탐색할 것”은  
- (A) 같은 레벨의 다른 개체들(범위 확장),  
- (B) 그 개체의 하위 구성요소(깊이 진입)  
둘 중 하나로 제한되고, **우선 (A)를 시도한 뒤 불가하면 (B)** 로 가면 된다.

#### (3) 구체적 매핑 예시 (결핍 → 탐색)

| 결핍 (무엇이 비어 있는가) | 먼저 시도할 탐색 (범위 확장) | 실패 시 탐색 (깊이 진입) |
|--------------------------|-----------------------------|---------------------------|
| output **grid**의 **size** | 다른 pair의 output grid size 비교 → 모두 같으면 그 size 사용 | (size는 보통 상위에서 정해지므로) 다른 결핍과 함께 처리되거나, 하위에서 “캔버스”로 유지 |
| output **grid**의 **contents** | 다른 grid 탐색: test input과 **같은** input을 가진 example의 output이 있는가? → 있으면 그 output 복사 (PaG1) | GRID 하위인 **OBJECT** 탐색 (한 grid 내 object 비교 → 다른 grid object → 다른 pair object) |
| output **grid**의 **color** (팔레트 등) | 다른 output grid의 color 집합과 비교·추론 | OBJECT/PIXEL 단계에서 색 매핑으로 처리 |
| 한 **object**의 속성 (위치, 형태 등) | 같은 grid 내 다른 object, 다른 grid의 object, 다른 pair의 object 순으로 비교 | 그 object의 **PIXEL** 단계 (픽셀 단위 변환) |

이 표를 **규칙 테이블**로 두고, 결핍 종류를 키로 “다음에 무엇을 탐색할지”를 찾으면 된다.

#### (4) 구현 시 필요한 것

- **결핍 표현**: `(레벨, 속성명, 맥락)` 같은 형태.  
  예: `(GRID, contents, output_for_test_0)`.
- **결핍 → 탐색 액션 테이블**: 위처럼 “결핍 종류 → [범위 확장 대상, 깊이 진입 대상]”을 정의.  
  새 결핍 타입이 생기면 테이블만 보강하면 됨.
- **실행 순서**:  
  1) 현재 결핍 목록에서 하나 선택 (예: 우선순위는 contents > size > color 등).  
  2) 해당 결핍에 대해 테이블에서 “범위 확장” 탐색 실행.  
  3) 채워지면 결핍 제거; 안 되면 “깊이 진입” 탐색으로 넘어가서 하위 레벨에서 같은 방식 적용.

정리하면, **“결핍이 무엇이기 때문에 어떤 것을 탐색한다”**는 것은  
- 결핍을 **(레벨, 속성)** 으로 명시하고,  
- “그 결핍을 채우는 방법 = 같은 레벨 다른 개체 vs 하위 레벨” 두 가지만 쓰며,  
- **결핍 종류별로 “먼저 볼 탐색(범위 확장)”과 “그 다음 볼 탐색(깊이 진입)”을 테이블로 고정**하는 방식으로 결정하면 된다.
