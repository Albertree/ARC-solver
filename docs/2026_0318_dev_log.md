# [2026_0318] SOAR cycle & WM 로그 정렬

오늘은 **SOAR 결정 사이클(cycle)** 뼈대를 실제로 동작시키고, WM 로그를 Soar 디버거 스타일에 더 가깝게 맞추는 작업을 했다.

---

## 1. 구현/수정한 흐름 요약

### 1-1. run_task → cycle 연결

- `run_task.py`
  - 태스크 로드 후, 다음 순서로 동작:
    1. `wm = WorkingMemory()`
    2. **Initial WM 덤프**  
       - `reset_wm_snapshot(wm)`  
       - `print_wm_triplets(wm, "Initial WM (before input)", step=0)`
    3. **환경 input function**  
       - `inject_arc_task(task, wm)` → `^io.input-link.task` 주입  
       - `print_wm_triplets(wm, "After input-link injection (before cycle)", step=0)`
    4. `elaborator = build_elaborator()` / `proposer = build_proposer()`
    5. `run_cycle(wm, elaborator, proposer, max_steps=0, ...)` (지금은 Step 1 elaborate 전에 break 되도록 0으로 고정)

→ 결과적으로 **초기 WM → input-link 주입으로 인한 변화(초록)** 만 본 뒤, 실제 사이클은 멈춘 상태. `max_steps`를 늘리면 바로 이어서 사이클 로그가 찍힌다.

### 1-2. cycle.run_cycle — 최소 동작 버전

- 파일: `agent/cycle.py`
- 구현된 것:
  - `run_cycle(wm, elaborator, proposer, max_steps, stop_on_goal, log_wm)`
  - `_elaborate(wm, elaborator)` — 단순 래퍼 (`elaborator.run(wm)`)
  - `_propose(wm, proposer)` — 후보 수집 + (루트 상태일 때만) 오퍼레이터 materialize
  - `_select(candidates, wm)` — `preferences.select_operator`로 선택, 루트에서만 `^operator O1`/`operator-application` 반영
  - `_apply(operator, wm)` — **오직 effect 호출 + 변화 감지(return 값)**, WM에 상태 슬롯 안 남김
  - `_handle_impasse(wm, trigger)` — 현재는 demo 수준의 no_candidates/failure 처리

#### 사이클 루프 형태

- 루프 본체 (요약):

```python
step = 0
while step < max_steps:
    if stop_on_goal and _s1_goal_satisfied(wm):
        break

    _elaborate(...)
    print_wm_triplets(... "After: elaborate")

    candidates = _propose(...)
    print_wm_triplets(... "After: propose")

    selected = _select(...)
    print_wm_triplets(... "After: select")

    if selected is None:
        cont = _handle_impasse("no_candidates")
        print_wm_triplets(... "After: impasse(no_candidates)")
        if not cont: break
        step += 1
        continue

    outcome = _apply(selected, wm)
    print_wm_triplets(... f"After: apply({selected.name})")

    if outcome == "failure":
        cont = _handle_impasse("failure")
        print_wm_triplets(... "After: impasse(failure)")
        if not cont: break
    elif wm.depth == 0 and outcome == "no_change":
        ok = wm.push_substate("no-change", "operator")
        print_wm_triplets(... "After: impasse(no-change)")
        if not ok: break

    step += 1
```

#### `_apply`의 설계 — WM에 op_status/selected_op를 **쓰지 않음**

- 변화 감지는 다음과 같이 **오직 `wme_records` 길이**로만 판단:

```python
def _apply(operator, wm) -> str:
    n_before = len(wm.wme_records)
    try:
        operator.effect(wm)
    except Exception:
        return "failure"
    n_after = len(wm.wme_records)
    if n_after == n_before:
        return "no_change"
    return "changed"
```

- Soar-style로 보면:
  - **solve-task** 같은 추상 오퍼레이터는 `effect()`에서 WM을 바꾸지 않으므로 `"no_change"`
  - 이 값만 보고 루트 상태(S1)에서 `push_substate("no-change", "operator")` 를 호출해 **오퍼레이터 no-change 임패스를 트리거**
  - **WM에는 `^op_status`, `^selected_op`, `^proposed_ops` 같은 메타 슬롯을 전혀 남기지 않는다.**

#### `_propose` — `^proposed_ops` 제거

- 과거 설계에는 S1에 `^proposed_ops` 슬롯을 두려 했으나,
  - Soar 디버거 스타일을 유지하기 위해 **preferences 는 `(S1 ^operator O1 +)` / `(O1 ^op-preference +)` 조합으로만 표현**하기로 결정.
- 현재 구현:

```python
def _propose(wm, proposer) -> list:
    candidates = proposer.propose(wm) or []
    # Soar-style: 별도의 ^proposed_ops WME는 만들지 않는다.
    if wm.depth == 0 and candidates:
        materialize_operator_proposals(wm, candidates)
    return candidates
```

→ 로그 상에서는:

- 제안 시: `(S1 ^operator O1 +)`  
- 선택 후: `(S1 ^operator O1 +)` + `(S1 ^operator O1)` (pref 없는 공식 적용 WME)

만 보이고, `^proposed_ops`는 등장하지 않는다.

#### `_select` — selected_op WME 제거

- 초기에 S1에 `^selected_op <Operator 객체>` 를 남겼다가, Soar와 어긋난다고 판단해 제거.
- 현재는:

```python
def _select(candidates, wm):
    sel = select_operator(candidates, wm)
    if sel is None:
        return None
    if wm.depth == 0:
        oid = _operator_id_for_name(wm.s1, sel.name)
        if oid:
            wm.s1["operator"] = oid
        mark_operator_selected(wm)  # ^operator O1 (pref 없는 줄) 추가
    return sel
```

→ 로그에는 여전히 `(S1 ^operator O1 +)` / `(S1 ^operator O1)` 조합만 있고, `^selected_op` 슬롯은 없다.

### 1-3. preferences.select_operator 구현

- 파일: `agent/preferences.py`
- 구현 내용:

```python
PREFERENCE_ORDER = [
    "solve-task",
    "select_target",
    "compare",
    "extract_pattern",
    "generalize",
    "descend",
    "predict",
    "verify",
    "submit",
]

def select_operator(candidates: list, wm) -> object:
    if not candidates:
        return None
    rank = {name: i for i, name in enumerate(PREFERENCE_ORDER)}

    def sort_key(op: object) -> tuple[int, int]:
        name = getattr(op, "name", "") or ""
        return (rank.get(name, 10_000), candidates.index(op))

    return min(candidates, key=sort_key)
```

- 즉, **우선순위 테이블** + **동순위 시 후보 목록 순서**를 tiebreak로 사용.

### 1-4. propose_wm — S1 오퍼레이터 슬롯 정리 헬퍼

- 파일: `agent/propose_wm.py`
- 새로 추가/정리한 함수:

```python
def clear_s1_operator_slots(wm) -> None:
    """
    S1에서 제안/선택/적용용 오퍼레이터 WME를 제거한다.
    상위 사이클을 다시 시작하거나 서브스테이트를 비운 뒤 S1로 돌아올 때 사용.
    """
    state = wm.s1
    for k in (
        "operator",
        "operator-application",
    ):
        state.pop(k, None)
    for k in list(state.keys()):
        if len(k) > 1 and k[0] == "O" and k[1:].isdigit():
            del state[k]
```

- 현재 용도:
  - `cycle._handle_impasse("no_candidates")` 에서 **서브스테이트(S2 이상)에서 후보가 완전히 없는 경우**:
    - `wm.pop_substate()` + `clear_s1_operator_slots(wm)` 로 **이전 S1 오퍼레이터 흔적을 전부 제거**하고, 다음 최상위 사이클에서 새로운 오퍼레이터를 제안/선택할 수 있도록 한다.
- Soar의 “i-support에 의한 자동 retract”를 완전히 구현한 것은 아니고, **임시로 수동 정리하는 helper** 라는 점을 분명히 인지.
  - 향후 S2 규칙이 실제로 S1 WM을 수정하게 되면, 이 헬퍼를 걷어내고 **상위 상태 변화 → 규칙 매칭 해제 → 자동 retract** 흐름으로 옮겨갈 계획.

### 1-5. wm_logger — Soar 형식에 맞춘 정렬/버그 수정

- 파일: `agent/wm_logger.py`
- 오늘 조정한 핵심 포인트:
  - **S1 attribute 정렬**:
    - 순서: `type`, `superstate`, `io`, `smem`, `epmem`, `current-task`, `operator`, `operator-application`
  - **서브스테이트(S2, S3, …) 정렬**:
    - 순서: `type`, `superstate`, `impasse`, `choices`, `attribute`, `quiescence`, `smem`, `epmem`, `item`, `item-count`, `non-numeric`, `non-numeric-count`
  - 빈 리스트 `[]` 처리 시 `_WME(..., depth)` 인자를 빠뜨려서 생기던 오류를 수정.
  - `^proposed_ops` 를 로그에 찍지 않도록, 아예 WM에서 해당 슬롯을 제거한 설계와 맞추어 정리.

→ 현재 로그 예시는 다음과 같이 나온다:

```text
[Step 0] Initial WM (before input)
  (S1 ^type state
      ^superstate nil
      ^io I1
      ^smem I4
      ^epmem I5)
    (I1 ^input-link I2
        ^output-link I3)
    (I4 ^id SM1)
    (I5 ^id E1)

[Step 0] After input-link injection (before cycle)
  (S1 ^type state
      ^superstate nil
      ^io I1
      ^smem I4
      ^epmem I5)
    (I1 ^input-link I2
        ^output-link I3)
      (I2 ^task 08ed6ac7)          ; ← 초록
    (I4 ^id SM1)
    (I5 ^id E1)
```

## 2. SOAR 구조적 디테일 — 오늘 합의된 규칙들

오늘 대화에서 정리된 Soar 구조 디테일 중, 실제 코드/로그에 반영된 것들을 요약한다.

### 2-1. State identifier 및 attribute 규약

- **최상위 상태**: `S1`
  - 최소 필수 슬롯:

```text
(S1 ^type state
    ^superstate nil
    ^io I1
    ^smem I4
    ^epmem I5
    ...)
```

  - 순서는 `type`, `superstate`, `io`, `smem`, `epmem`, 그 외(예: `current-task`, `goal`, `focus`, `operator`, ...) 이다.
  - `^io` 아래:

```text
(I1 ^input-link I2
    ^output-link I3)
```

- **서브스테이트(임패스)**: `S2`, `S3`, …

```text
(S2 ^type state
    ^superstate S1
    ^impasse no-change | failure | no_candidates
    ^choices none | multiple | constraint-failure
    ^attribute operator | ...
    ^quiescence true
    ^smem I6
    ^epmem I7
    [^item ...]
    [^item-count N]
    [^non-numeric ...]
    [^non-numeric-count M])
```

- **smem / epmem 순서**
  - S1, S2 모두 `^io` 뒤에 `^smem`, 그 다음 `^epmem` 순으로 고정.

### 2-2. Operator 및 preference 표기법

- **S1에서의 operator 제안/선택**
  - 제안(Propose) 직후:

```text
(S1 ^operator O1 +)
(O1 ^name solve-task
    ^task-id 08ed6ac7
    ^op-preference +)
```

  - 선택(Select) 직후:

```text
(S1 ^operator O1 +)
(S1 ^operator O1)            ; pref 없는 공식 적용 WME 하나 추가
```

  - `^proposed_ops`, `^selected_op`, `^op_status` 같은 추가 슬롯은 **사용하지 않는다.**
  - preference 기호(`+`, `!`, `~`, `-`)는 앞으로도 **`^operator` / `^op-preference` 를 통해서만 표현한다.

### 2-3. Operator no-change impasse

- **추상 오퍼레이터**: `SolveTaskOperator`
  - 의도:
    - S1에서 ARC 태스크 전체를 “풀어라”라는 **상위 목표**만 던지는 추상 operator.
    - 실제 비교/수집/generalize/descend 등은 **하위 상태(S2 이후)** 에서 구체 operator들이 수행.
  - 구현:
    - `effect()` 본문은 **WM을 전혀 바꾸지 않고 `return`만**.

- **no-change 감지와 임패스 생성**
  - `_apply` 에서:
    - `effect()` 호출 전후 `wme_records` 길이가 같으면 `"no_change"`.
  - 루트 상태(S1)에서 `"no_change"` 이면:

```python
ok = wm.push_substate("no-change", "operator")
```

→ 로그 예시:

```text
[Step 0] After: apply(solve-task)
  (S1 ^type state
      ^superstate nil
      ^io I1
      ^smem I4
      ^epmem I5
      ^current-task 08ed6ac7
      ^operator O1 +
      ^operator O1)
  (O1 ^name solve-task
      ^task-id 08ed6ac7)

[Step 1] After: elaborate        ; S2 활성화 이후에는 여기에 S2 블록도 함께 찍힘
  (S2 ^type state
      ^superstate S1
      ^impasse no-change
      ^choices none
      ^attribute operator
      ^quiescence true
      ^smem I6
      ^epmem I7)
```

- 이 시점에서도 **S1의 `^operator O1 +`/`O1` 블록은 그대로 유지**된다.
  - Soar의 i-support 관점에서 “상위 상태 WM이 아직 변하지 않았으므로 제안 규칙이 여전히 매칭 중”인 상태와 대응.
  - substate에서 실제로 S1 WM을 바꾸는 규칙/오퍼레이터를 채워 넣은 뒤,
    - 상위 WM 변화로 인해 발화 조건이 깨지면 **제안이 자동 retract되는 방향**으로 후속 설계를 진행할 예정.

## 3. 앞으로 채워야 할 것 (오늘 기준)

1. **S2용 구체 오퍼레이터 및 규칙**
   - 예: `SelectTargetOperator`, `CompareOperator`, `ExtractPatternOperator`, `GeneralizeOperator`, `DescendOperator` 등을 **substate에서 실제로 작동**하도록 설계.
   - S2에서 S1의 `goal.subgoals` / `found` / 기타 플래그를 수정해 “Result”를 올리는 패턴 정립.

2. **Result → 상위 상태 WM 업데이트 패턴**
   - S2가 끝났을 때 S1에 무엇을 어떻게 써야 하는지 (예: `test_k.status = "solved"` / `found[test_k] = grid`) 를 구체화.

3. **자동 retract / i-support 방향성**
   - 현재는 `clear_s1_operator_slots` 로 S1 operator 영역을 수동 정리하는 임시 구조.
   - 향후:
     - S1의 변화로 인해 `SolveTaskRule` 등의 condition이 깨지면,
     - 그 규칙이 만든 `^operator O* +` / `O*` 노드를 **자연스럽게 retract**하도록 구조화.
   - 완전한 Soar-style i-support (규칙 인스턴스 ↔ WME 링크 추적)는 그 다음 단계의 과제로 남겨둔다.

4. **`max_steps` / `stop_on_goal` 튜닝**
   - 지금은 디버깅 편의를 위해 `run_task.py` 에서 `max_steps=0` 고정.
   - S2 로직이 어느 정도 채워지면:
     - “한 decision cycle = 한 operator apply” 원칙을 유지하면서,
     - 적절한 `max_steps` / 종료 조건을 설정해 end-to-end ARC 풀이 루프까지 연결.

## 4. 오늘 변경에 맞춘 README 업데이트 요약

- README의 이전 서술 중:
  - “WM에 `proposed_ops` / `selected_op` / `op_status`가 항상 기록된다”는 부분은 **현재 구현과 다름**.
  - 오늘 변경으로:
    - **operator preference** 는 `(S1 ^operator O1 +)` / `(O1 ^op-preference +)` 로만 표현.
    - no-change / failure 여부는 **cycle 내부에서만 계산**하고, WM 슬롯으로 남기지 않는다.
    - `proposed_ops` 리스트는 **WM에서 제거**되었고, Soar-style WD 형식만 유지한다.
- README에는 이 파일에서 정리한 내용 중:
  - S1/S2 attribute 순서 (`type`, `superstate`, `io`, `smem`, `epmem`, ...),
  - operator 및 preference 표기법,
  - operator no-change impasse의 구조
  를 반영해 **구조적 디테일 섹션을 갱신**했다. (루트 README 수정 내용은 해당 파일 참고)
